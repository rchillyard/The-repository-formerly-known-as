# Paper deletions

Material removed from `HuskySort.tex`, kept here so that it can be consulted or restored without
digging through git. Each entry says what it was, why it went, and what replaced it.

Checked against the tex on 2026-09-05: nothing here has been removed yet, and every line number below
is still accurate.

---

## Table `HSComp` — relative sort times, HuskySort / dual-pivot quicksort / system sort

**Status: PROPOSED for deletion, not yet removed.** See "What removing it costs" — it has seven
inbound references and two of them are load-bearing prose, so this needs a decision rather than a
delete. The table itself is at tex 1080–1103.

### Why it should go

- It is measured on the machine of Table `SysEnvOriginal`: a 2017 MacBook Pro with a quad-core Intel i7,
  running **Java 1.8.0_152**. Two JVM generations back and a different instruction set from everything
  else in the paper. It is not the only such table — `TimvsInsertion` and `Improvements Summary` are
  there too, see below — but it is the only one that says so (tex 1078), which is why it is the one that
  gets noticed.
- It **cannot be rebuilt.** It is a thirteen-point sweep from N=1,000 to N=4,000,000, normalised so
  that dual-pivot quicksort is 1.00. The JMH suite runs none of those sizes: 20,000/100,000/500,000
  for numerics and tuples, 32,000/200,000/1,000,000 for strings. Reproducing it would mean a separate
  experiment, not a re-run.
- It is **superseded.** Tables `HS_BM_N`, `HS_BM_S` and `HS_BM_T` make the same comparison on the
  machine of record, in absolute milliseconds with 99.9% confidence intervals, which normalised ratios
  cannot offer.

### What removing it costs

Seven references, of which the first two need real prose rather than a pointer swap:

| line | what it does | proposed treatment |
| ---: | --- | --- |
| 652 | quotes its numbers as a worked example — "HuskySort takes a normalized time of 0.93, compared with 1.00 for quicksort and 1.45 for Timsort" | **needs rewriting** with a figure from `HS_BM_S`; there is no dual-pivot column for strings, so either the normalisation changes or the example moves to tuples |
| 1284 | **the hardest one, and worse than "cites it".** It builds an argument on the table's shape: HuskySort's advantage over dual-pivot *shrinks* from 0.60 at N=1,000 to 0.97 at N=4,000,000, "which would undermine confidence that the advantage is durable at larger scale", and radix's advantage is then shown not to shrink that way. Delete the table and the contrast has nothing to stand on | **needs rewriting, or the table stays.** Either keep enough of `HSComp` to support it, or make the same point from `RadixImprovements` alone — the margin is 1.5x or greater at every size and type, which tex 1289 already says |
| 807 | names it as what `SysEnvOriginal` measured | drops out anyway when §Implementation is rewritten |
| 1034 | "refer to tables `Comparison` and `HSComp`" | drop `HSComp` from the pair. `Comparison` (tex 1059–1073) is a table of *theoretical* array-access counts, not a measurement, so it is unaffected by any of this and stays |
| 1075 | "Table `HSComp` was generated by sorting arrays of random English words" | delete with the table |
| 1138 | "Please refer to table `HSComp`" | point at `HS_BM_S` |

That is six lines for seven references, 1034 carrying two.

## Notes on other candidates

### Table `Improvements Summary` (tex 1232–1249) — the strongest remaining candidate after `HSComp`

"Advantage over Timsort", quoted as ranges over size bands such as "4,000—500,000 elements". Two
problems, and the second is the serious one.

- **It cannot be rebuilt.** JMH's three sizes per type cannot reproduce a range stated over a continuous
  band, exactly as with `HSComp`.
- **It is undated and unattributed.** Unlike `HSComp`, nothing in the text says which machine produced
  it. A reader has no way to know it is not from the machine of record, which makes it worse than
  `HSComp` rather than better — `HSComp` at least declares itself (tex 1078).

Only two inbound references, both easy: tex 682 ("summarized later in Table …") and tex 1230 ("Please
refer to table …"). Both could point at `RadixImprovements` or at `HS_BM_N`/`HS_BM_S`/`HS_BM_T`
instead. **This is a cheaper deletion than `HSComp` and buys more, and it should probably go first.**

### Table `TimvsInsertion` (tex 1109–1132) — the third old-machine table

Timsort against insertion sort as the cleanup pass, in milliseconds, over the same thirteen sizes as
`HSComp` (N=1,000 to 4,000,000) and so from the same machine and the same era, though like `Improvements
Summary` it never says so. **Not proposed for deletion**, for one good reason: it is the only evidence in
the paper for the choice of Timsort in step 3, and the effect it shows is enormous — 2,424 ms against
11,018 ms at N=4,000,000. A 4.5x result does not become wrong on a newer JVM. If it stays, it needs a
sentence naming its machine, as `HSComp` already has.

**Table `Comparison` (tex 1059–1073) is not in this set.** It counts array accesses from the model of
§sec:radix and never touched a benchmark, so no machine attaches to it.

With `HSComp`, `Improvements Summary` and `TimvsInsertion`, that is the whole of what §7 of
`Paper edits pending.md` has left to resolve.

### Figure `usecase` (`UseCaseGuidance.pdf`, tex 1441–1466) — **RESOLVED**

Two band edges had moved (System sort now yields at N=20 rather than 50; insertion sort takes over at 50
rather than 100), and the matplotlib script that drew it had not been kept. Redrawn in TikZ as
`paper/UseCaseGuidance.tex`, which compiles to the same filename with `pdflatex`. The figure is now
source rather than an artefact, so the next time a crossover moves it can simply be edited.

Two changes since: an **MSD radix sort band** was added (it wins the right-hand end from N=200,000, and
a figure recommending what to reach for cannot omit the algorithm that wins there), and the band spacing
was compressed from 1cm to 0.78cm, the five-band version having pushed the paper from 15 pages to 16.

The figure's own caveats are documented in the generator's header comments rather than here: MSD's band
starts at 32,000 because that is the smallest size at which it was measured, and the chart is English
text only because MSD's alphabet cannot represent either Chinese corpus.
