# Paper deletions

Material removed from `HuskySort.tex`, kept here so that it can be consulted or restored without
digging through git. Each entry says what it was, why it went, and what replaced it.

**Three things were removed on 2026-09-07**, all to get within ACDA27's 12-page limit: Tables `HSComp`
and `Improvements Summary`, and Figure `usecase`. Together they took the body from 13.0 pages to
**12.0**, which is within the limit. Line numbers in each entry are as they stood *before* that entry's
removal, since that is what makes them readable against the verbatim copies kept here.

`TimvsInsertion` is the only old-machine table still in the paper, and it is kept deliberately.

---

## Table `HSComp` — relative sort times, HuskySort / dual-pivot quicksort / system sort

**Status: REMOVED 2026-09-07**, on Robin's instruction, together with `Improvements Summary`. All
seven inbound references were resolved; see the table below for what each became. The build is clean,
with no undefined references. Between them the two tables bought about six-tenths of a page; Figure
`usecase` was removed afterwards for the remaining four-tenths.

### Why it should go

- It is measured on the machine of Table `SysEnvOriginal`: a 2017 MacBook Pro with a quad-core Intel i7,
  running **Java 1.8.0_152**. Two JVM generations back and a different instruction set from everything
  else in the paper. It is not the only such table — `TimvsInsertion` and `Improvements Summary` are
  there too, see below — but it is the only one that says so (tex 1078), which is why it is the one that
  gets noticed.
- It **cannot be rebuilt.** It is a thirteen-point sweep from N=1,000 to N=4,000,000, normalised so
  that dual-pivot quicksort is 1.00. The JMH suite runs none of those sizes: 20,000/100,000/500,000
  for numerics and tuples, 32,000/200,000/1,000,000 for strings. Reproducing it would mean a separate
  experiment, not a re-run.
- It is **superseded.** Tables `HS_BM_N`, `HS_BM_S` and `HS_BM_T` make the same comparison on the
  machine of record, in absolute milliseconds with 99.9% confidence intervals, which normalised ratios
  cannot offer.

### What removing it costs

Seven references, of which the first two needed real prose rather than a pointer swap. Line numbers are
as they were before the removal.

| line | what it did | what was actually done |
| ---: | --- | --- |

### One thing the rewrite exposed

`HS_BM_N`, which line 1138 now points at, shows QuickHuskySort **slower** than the dual-pivot baseline
on three of its five numeric types: Integer 87.9 against 81.7, Double 93.5 against 92.8, Long 99.3
against 90.5. So the conclusion's "HuskySort is always faster than dual-pivot quicksort" is not merely
overstated, as §4.1 of `Paper edits pending.md` had it — **it is contradicted by a table in the same
paper**, and by the very table a reader is now sent to. Not fixed here; §4.1 has been upgraded from
"should soften" to "must fix" and carries the numbers.

## Notes on other candidates

### Table `Improvements Summary` — **REMOVED 2026-09-07**

"Advantage over Timsort", quoted as ranges over size bands such as "4,000—500,000 elements". Two
problems, and the second is the serious one.

- **It cannot be rebuilt.** JMH's three sizes per type cannot reproduce a range stated over a continuous
  band, exactly as with `HSComp`.
- **It is undated and unattributed.** Unlike `HSComp`, nothing in the text says which machine produced
  it. A reader has no way to know it is not from the machine of record, which makes it worse than
  `HSComp` rather than better — `HSComp` at least declares itself (tex 1078).

Two inbound references, both resolved on removal:

| line | what it did | what it became |
| ---: | --- | --- |
| 682 | "we still find very significant gains, summarized later in Table `Improvements Summary` (§sec:summary)" — the worst case, Chinese in UTF8 | points at `HS_BM_S`, which has the Chinese rows in absolute ms with intervals |
| 1230 | "Please refer to table `Improvements Summary`" | the paragraph introducing it was rewritten to quote the three benchmark tables directly, with the ranges recomputed from them |

The multiplier-versus-percentage aside that preceded it (tex 1226–1229) went with it: the same point is
made again forty lines later for `RadixImprovements`, so it was saying it twice.

### Table `TimvsInsertion` (tex 1082–1105 after the removal) — now the *only* old-machine table

Timsort against insertion sort as the cleanup pass, in milliseconds, over the same thirteen sizes as
`HSComp` (N=1,000 to 4,000,000) and so from the same machine and the same era, though like `Improvements
Summary` it never says so. **Not proposed for deletion**, for one good reason: it is the only evidence in
the paper for the choice of Timsort in step 3, and the effect it shows is enormous — 2,424 ms against
11,018 ms at N=4,000,000. A 4.5x result does not become wrong on a newer JVM. **It now has the machine
attribution it was missing**: tex 806 was repointed here from `HSComp`, so §Implementation names this
table as what `SysEnvOriginal` measured.

**Table `Comparison` (tex 1059–1073) is not in this set.** It counts array accesses from the model of
§sec:radix and never touched a benchmark, so no machine attaches to it.

With `HSComp` and `Improvements Summary` gone and this one attributed, §7 of
`Paper edits pending.md` is closed.

### Figure `usecase` (`UseCaseGuidance.pdf`) — **REMOVED 2026-09-07**

Removed on Robin's decision, to recover the last four-tenths of a page against ACDA27's 12-page limit.
Of the four options weighed — move it to the appendix, drop it, shrink it to one column, or trim §6.5's
prose instead — dropping it was chosen, and it is the one with the best independent argument behind it.

**Why dropping beats relocating.** Robin's question of 2026-09-06 was whether the figure was justifiable
at all, given that "all we seem to have are sizes". Table `Guidance` was written in answer to that: the
three factors decide the choice of sort, and array size settles nothing until all three are answered. A
figure organised entirely along the size axis therefore argues for a way of choosing that the paper had
already stopped recommending. It was redundant against the table, not merely relocatable.

**Two inbound references, both resolved:**

| line | what it did | what it became |
| ---: | --- | --- |
| 1396 | Table `Guidance`'s last row: "None of the above settles it, or the keys are strings & see Figure ~\ref{fig:usecase}" | points at the crossover measurements in the prose that follows the table, which is where those figures actually live |
| 1434 | "Figure~\ref{fig:usecase} summarizes the String-key guidance above graphically." | deleted with the figure |

References to `\S~\ref{sec:usecase}` at tex 624 and 1490 are to the *section*, not the figure, and are
unaffected.

**`paper/UseCaseGuidance.tex` is kept, not deleted.** It no longer participates in the build — nothing
includes `UseCaseGuidance.pdf` now — but it is a working TikZ generator with the band edges documented
in its header, and a journal version of this paper under a looser page limit would plausibly want it
back. Deleting it would throw away the only reason the figure was recoverable in the first place. Robin
may of course prefer it gone.

### Its earlier history, kept for the record

Two band edges had moved (System sort now yields at N=20 rather than 50; insertion sort takes over at 50
rather than 100), and the matplotlib script that drew it had not been kept. Redrawn in TikZ as
`paper/UseCaseGuidance.tex`, which compiles to the same filename with `pdflatex`. The figure is now
source rather than an artefact, so the next time a crossover moves it can simply be edited.

Two changes since: an **MSD radix sort band** was added (it wins the right-hand end from N=200,000, and
a figure recommending what to reach for cannot omit the algorithm that wins there), and the band spacing
was compressed from 1cm to 0.78cm, the five-band version having pushed the paper from 15 pages to 16.

The figure's own caveats are documented in the generator's header comments rather than here: MSD's band
starts at 32,000 because that is the smallest size at which it was measured, and the chart is English
text only because MSD's alphabet cannot represent either Chinese corpus.
